# Lab module slices 1b and 2: one request per test, and reception

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Orders become one FHIR ServiceRequest per test with fixed ids, the Lab order form stops entering results, unauthorised results stay out of the warehouse, and a Reception page finds or registers an order, links its patient, receives its sample and corrects a typo.

**Architecture:** Order ids and the per-test split live in `@openldr/forms`, beside the extractor that builds orders today. The warehouse filter lives in the `@openldr/db` projection. Reception logic is one module in `@openldr/bootstrap` (`lab-reception.ts`) that the routes in `apps/server/src/lab-routes.ts` call; its writes go through the FHIR store, `correct` from slice 1a, and a new requisition lookup table. The studio gets a Reception page under `apps/studio/src/lab/`. Bench work has no CLI (spec 5.11); the one maintenance command is the lookup rebuild.

**Tech stack:** TypeScript, zod, Kysely on Postgres (internal) and Postgres, SQL Server or MySQL (warehouse), Fastify, React with shadcn, vitest, pg-mem.

**Spec:** `docs/superpowers/specs/2026-11-22-lab-module-design.md`, sections 5.0, 5.3, 5.4 (first paragraph), 5.6 (second paragraph), 5.9, 5.10 (Registered, Typo corrected, Received rows), 7 (slices 1b and 2).

## Where the code differs from the spec, and the rulings this plan makes

These come from reading the code on 2026-11-22. Each is a call the operator should check.

1. **Fixed ids include the facility.** The spec says ids come from the requisition number and the test code. The form entries rule lets two sites use the same number (`136_form_entries.ts:38-40`), so an id from those two alone would merge two sites' orders. The id is built from the requesting facility, the requisition number and the test.
2. **Old orders stay as stored.** Every order saved through the Lab order form so far is one ServiceRequest holding all its tests as codings, and the warehouse kept only the first test (`relational/service-request.ts:15`, `relational/extract.ts:24-32`). This plan does not rewrite them. Reception reads all their codings when it shows them. Only new orders are one per test.
3. **The Lab order form keeps its order rejection field until slice 3.** The spec moves rejection into the lab pages, but the rejection page is slice 3. Removing it now would leave a lab with no way to reject an order. Only the results field goes in this plan.
4. **The form builder stops offering the test details field.** Other forms keep working as they are. No new form can save final results round authorisation.
5. **A skipped result deletes its warehouse row.** Skipping alone leaves old rows (`relational-writer.ts:63,79-80`), so a preliminary or registered Observation removes its `lab_results` row, and external migration 028 removes the rows already there.
6. **Sync is unchanged.** A preliminary Observation still syncs to central as FHIR; central's own warehouse filters it the same way.
7. **A requisition lookup table.** Nothing indexes the requisition number today (FHIR store has no search index; `lab_requests.request_id` is unindexed text). Internal migration 139 adds `lab_requisitions`, filled from existing ServiceRequests, kept current by the projection hook for every source, with `openldr lab requisitions rebuild` to rebuild it.
8. **Reception gets its own routes.** The Reception role lacks `forms.view`, `facilities.view`, `terminology.view` and `patients.view_identifiers`, so every existing lookup refuses it. New `/api/lab/...` routes gate on `lab.receive`.
9. **Patient search shows a patient only on a strong match.** A search returns a patient only for an exact identifier, or a name with a full date of birth. This lets Reception confirm a patient without the identifier capability.
10. **Patient registration takes a date of birth or an age.** With an age, the birth date is estimated as 1 January of the year it implies, and an extension `urn:openldr:ext:birthdate-estimated` says so (operator preference: a stated estimate over nothing).
11. **Sex is checked against the Patient schema's own list,** not `validateCode`, which still answers false for catalog value sets (slice 1a P1).
12. **What a typo correction may change:** priority, clinician, notes and the patient link. The facility, the requisition number and the tests are part of the ids. A wrong number or test list is fixed by voiding and registering again.
13. **One Specimen per sample type per requisition,** with a fixed id from the order key and the type, `request` pointing at the tests it serves.
14. **An order registered at the desk carries `meta.tag` `urn:openldr:cs:order-origin|lab-desk`,** so slice 3 can refuse to return it to a site.
15. **"Barcode" means the requisition number printed as a barcode.** A scanner types it into the same box. No separate barcode field.

## Review focus

1. The same requisition number at two facilities: two separate orders with different ids, and Reception shows both with their facility. (Tasks 1, 5)
2. A retried submit or a retried register with the same facility, number and tests: the same ServiceRequest ids are updated, never copied. (Tasks 1, 5)
3. An old multi-coding order found at Reception: every test is listed, not only the first, and receiving links its Specimen to that one ServiceRequest. (Tasks 5, 6)
4. A patient registered at Reception and then searched for at once, before the warehouse catches up: the page keeps the patient it just made and links it, and does not depend on the search. (Tasks 6, 8)
5. An Observation that was final and is later corrected to preliminary: its `lab_results` row disappears. (Task 3)

### Task 5: Reception service, orders

**Files:**
- Create: `packages/bootstrap/src/lab-reception.ts` and `lab-reception.test.ts`; wire it into the app context in `packages/bootstrap/src/index.ts`

**Interfaces:**

```ts
export interface ReceptionOrder {
  requisition: string; facility: { code: string; display: string | null } | null;
  origin: 'lab-desk' | 'form' | 'other';
  patient: { id: string; display: string } | null;
  priority: string | null; clinician: string | null; note: string | null;
  tests: Array<{ serviceRequestId: string; system: string; code: string; display: string | null; status: string }>;
  specimens: Array<{ id: string; type: { system: string; code: string; display: string | null } | null; condition: string | null; receivedTime: string | null }>;
}
export class ReceptionError extends Error { readonly reason: 'not-found' | 'invalid' | 'conflict' }
findOrders(requisition: string): Promise<ReceptionOrder[]>;   // one per facility
registerOrder(input: { requisition: string; facilityCode: string; patientId: string; tests: Array<{ system: string; code: string }>; priority?: string; clinician?: string; note?: string }, who: string): Promise<ReceptionOrder>;
correctOrder(input: { requisition: string; facilityCode: string | null; changes: { priority?: string | null; clinician?: string | null; note?: string | null; patientId?: string }; reason: string }, who: string): Promise<ReceptionOrder>;
```

- `findOrders` reads `findByRequisition`, loads the requests with `fhirStore.get`, and groups them by facility. A test list comes from every coding of an old multi-coding request: one entry per catalog-system coding, each with that request's id. Specimens come from `labSpecimenId` lookups and any Specimen whose `request` names one of the ids.
- `registerOrder` refuses an existing requisition and facility with `conflict`, and refuses unknown or disabled tests with `invalid`. It writes the per-test requests with `labOrderId`, `meta.tag` origin `lab-desk`, `subject` = `Patient/<patientId>`, through `persistResources` so they validate. It indexes them with `indexRequisitions` in the same call.
- `correctOrder` calls `fhirStore.correct` once per request of that order, with the same reason.

### Task 6: Reception service, patients and samples

**Files:**
- Modify: `packages/bootstrap/src/lab-reception.ts` and its test

**Interfaces:**

```ts
searchPatients(q: { identifier?: string; name?: string; birthDate?: string }): Promise<Array<{ id: string; name: string; birthDate: string | null; gender: string | null; identifiers: Array<{ system: string; value: string }> }>>;
```

- `searchPatients` answers only an exact identifier, or a name with a full `YYYY-MM-DD` birth date. Anything else returns `[]`. It reads the warehouse `patients` and `patient_identifiers`, like `patient-index.ts`, but without masking, because the rule above limits what it shows.
- `registerPatient` needs `birthDate` or `ageYears` (0 to 130). From an age it writes `birthDate` = `${year - ageYears}-01-01` and the extension `urn:openldr:ext:birthdate-estimated` = true. `gender` is checked against `Patient.shape.gender`. The id is a random UUID. It saves through `persistResources` with a Provenance naming `who`.
- `receiveSample` writes or updates one Specimen with id `labSpecimenId(facility, requisition, type)`:
  - `status` = available;
  - `receivedTime` = the input or now;
  - `type`;
  - `condition` = [condition] when given;
  - `subject` = the order's subject;
  - `request` = the chosen request ids, or all of the order's.

  It also writes a Provenance with `target` = that Specimen version, `agent.who` = who, and activity v3-DataOperation `CREATE` (`UPDATE` when the Specimen existed). A condition must be in `urn:openldr:valueset:sample-condition` (`ops.expand`).
- `sampleChoices` returns the specimen types the catalog lists for the order's tests (union).
