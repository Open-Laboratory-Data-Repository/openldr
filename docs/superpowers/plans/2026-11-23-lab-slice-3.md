# Lab module slice 3: return a request, reject a sample, redraw

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** At Reception, the lab can return a request to its site and take it back when corrected, reject an unfit sample or a single test and ask for a redraw, and link the redraw to the order it replaces. Every step is FHIR R4.

**Architecture:** The logic is a new module `packages/bootstrap/src/lab-rejection.ts`, beside `lab-reception.ts`, reusing its helpers. Writes go through `fhirStore.correct` (status changes, with a Provenance) and `persistResources` (new Task, Specimen and Observation records). New routes go in `apps/server/src/lab-routes.ts`. The studio gets five sheets in `apps/studio/src/lab/` and new items in the order panel's dots menu. One internal migration seeds the task codes, gives Lab Technician `lab.reject`, and removes the rejection field from the Lab order form. Bench work has no CLI (spec 5.11), and this slice adds no admin setting, so it adds no CLI command.

**Tech stack:** TypeScript, zod, Kysely on Postgres, Fastify, React with shadcn, vitest, pg-mem.

**Spec:** `docs/superpowers/specs/2026-11-22-lab-module-design.md`, sections 5.1, 5.4 (second and third paragraphs), 5.10 (Returned to site, Corrected by site, Sample rejected, Redraw rows), 7 (slice 3).

## Where the code differs from the spec, and the rulings this plan makes

Read from the code on 2026-11-23. Each is a call the operator should check.

1. **The lab marks a returned request as corrected.** The spec says the Task completes "when the site sends the corrected request back". On one shared install, a site cannot send it: re-entering a live order is refused (`packages/bootstrap/src/form-entries.ts:262-273`), and the site's screen for hand-backs is a non-goal (spec section 3). So Reception gets "Corrected by site". It applies the site's corrections (the fields a typo correction may change) with a reason, sets the requests back to `active`, and completes the Task. If wrong: a site cannot correct its own request until the site slice. The FHIR records are the same either way.
2. **One return Task per order, not per test.** An order is now one ServiceRequest per test. The Task's `focus` is the first test's request, and `basedOn` names every test's request. Task id `labTaskId('correct-request', orderKey(facility, requisition))`. A second return of the same order reuses the id as a new version. If wrong: a reader expecting one Task per request finds one per order.
3. **Task codes are a local code system.** HL7's `task-code` has no "recollect". Migration 140 seeds `urn:openldr:cs:lab-task` with `correct-request` and `recollect-sample`. The system and the two codes are workflow constants in source, like `LAB_DESK_ORIGIN`, not clinical vocabulary. If wrong: a hub reads a local code.
4. **A redraw needs a new requisition number.** Order ids are fixed from facility, number and test (`packages/forms/src/extract/order-ids.ts`), so the same number names the rejected request. The desk registers the redraw, or finds the site's new form order, under a new number. Then it uses "Replaces a rejected order" with the old number. That sets `replaces` on each test whose code matches and completes the redraw Task. If wrong: a lab that reuses numbers for redraws must add a suffix.
5. **Rejecting a sample revokes every request it serves.** The Specimen becomes `unsatisfactory` with the chosen condition. Each request in its `request` becomes `revoked` with the existing `urn:openldr:ext:rejection` extension, so the warehouse's `rejection_code` fills as today (`packages/db/src/relational/request-facts.ts:50-74`). The reason comes from `urn:openldr:valueset:order-reject-reason`, as the spec says. A sample never received gets `receivedTime` now, because it is in hand. If wrong: a sample serving two tests cannot be rejected for one only. Reject the test instead.
6. **Rejecting one test writes what CE writes today, plus a revoke.** It writes a cancelled Observation with `dataAbsentReason` from `urn:openldr:valueset:test-reject-reason`, the shape `packages/db/src/relational/observation.ts:23-24` projects. That test's request also becomes `revoked` with the rejection extension, so it leaves the worklist. Observation id `labRejectionObservationId(serviceRequestId)`. If wrong: one test has two records of its rejection.
7. **Asking for a redraw is a switch, on by default.** A duplicate or wrong-patient rejection may need no new sample. The redraw Task has `focus` = the Specimen (sample rejection) or the request (test rejection), `basedOn` = the revoked requests, and `owner` = the requesting facility. Id `labTaskId('recollect-sample', focusId)`. If wrong: one more switch on the sheet.
8. **What a returned order may still do.** It can still be received and rejected. It cannot get a typo correction, because the site corrects it. A desk order is never returned (spec 5.4). Rejecting a returned order's sample sets its open return Task to `cancelled`. If wrong: a desk clerk cannot fix a typo on a returned request without marking it corrected.
9. **Lab Technician gains `lab.reject`.** The spec says "Reception or a technician rejects the sample", but section 5.1 gives the technician only `lab.results.enter` and `lab.worklist.view`. Migration 140 grants it once, as 137 granted the slice 1a keys. If wrong: a technician can also return a request to its site.
10. **The Lab order form loses its rejection field.** Migration 138 kept it "until the lab's rejection page ships (slice 3)". Migration 140 removes `fld-ord-rejection` by exact match, only from an unedited form, and moves the starter pack to version 7, as 138 did for Results. Other forms keep the field. If wrong: a site that rejected at collection now asks the lab to.
11. **Who the Task names.** `owner` is the requesting facility, in the shape `requesterFacility` reads. `requester` is the lab, as a display from the Laboratory settings name, or "Laboratory" when unset. `statusReason` is the reason coding. If wrong: the lab has no identifier on the Task.

## Review focus

1. Returning a desk order (`lab-desk` tag) is refused, and so is returning an order already on hold. (Task 2)
2. Return, mark corrected, return again: the same Task id gets a third version, `requested` again, and the history keeps all three. (Task 2)
3. A sample serving two tests is rejected: both requests are `revoked` with the extension, and one redraw Task names both in `basedOn`. (Task 2)
4. "Replaces a rejected order" with a number at another facility, or with no matching test, is refused and writes nothing. (Task 2)
5. A retried reject after a network drop writes no second redraw Task and no second Observation. Fixed ids make it an update, and a request already revoked is not revoked again. (Task 2)

### Task 2: Rejection service

**Files:**
- Create: `packages/bootstrap/src/lab-rejection.ts` and `lab-rejection.test.ts`; wire it into the app context in `packages/bootstrap/src/index.ts`.
- Modify: `packages/bootstrap/src/lab-reception.ts`. Export the helpers this module reuses (`groups`, `findOne`, `isDeskOrder`, `correctAll`, `specimensOf`, `conditionCoding`, `liveTests`), and extend `ReceptionOrder`.

**Interfaces:**

```ts
// added to ReceptionOrder
returned: { reason: { code: string; display: string | null }; by: string | null; at: string } | null; // the open return Task
redraws: Array<{ taskId: string; status: 'requested' | 'completed'; focus: string; replacedBy: string | null }>;
// added to each entry of ReceptionOrder.tests
rejection: { code: string; display: string | null } | null;

interface LabRejection {
  returnOrder(i: { requisition: string; facilityCode: string | null; reasonCode: string; note?: string }, who: string): Promise<ReceptionOrder>;
  markCorrected(i: { requisition: string; facilityCode: string | null; changes: CorrectChanges; reason: string }, who: string): Promise<ReceptionOrder>;
  rejectSample(i: { requisition: string; facilityCode: string | null; specimenTypeCode: string; conditionCode: string; reasonCode: string; redraw: boolean }, who: string): Promise<ReceptionOrder>;
  rejectTest(i: { serviceRequestId: string; reasonCode: string; redraw: boolean }, who: string): Promise<ReceptionOrder>;
  linkRedraw(i: { requisition: string; facilityCode: string | null; replacesRequisition: string }, who: string): Promise<ReceptionOrder>;
}
```

`CorrectChanges` is the `changes` type `correctOrder` already takes. Errors are `ReceptionError` with `not-found`, `invalid` or `conflict`. Reason codes are checked against their value set by `$expand`, as `conditionCoding` checks conditions.

- `returnOrder` refuses a desk order and an order already on hold, with `conflict`. It sets every live request `on-hold` through `correctAll`, with the reason's display. It writes the return Task (rulings 2 and 11) with `status` `requested`, `intent` `order`, `authoredOn` now, and the note in `note`.
- `markCorrected` refuses an order with no open return Task. It applies `changes` and `active` through `correctAll` with the reason, then sets the Task `completed`.
- `rejectSample` and `rejectTest` follow rulings 5 to 8. A request already revoked is left alone.
- `linkRedraw` follows ruling 4. Both orders must be at the same facility. It sets `replaces` through `correct` on each matching live test, with the reason "Redraw of <old number>". Then it sets each matching redraw Task `completed`.
- `findOrders` fills the new fields by reading Tasks by their fixed ids, never by a scan.
