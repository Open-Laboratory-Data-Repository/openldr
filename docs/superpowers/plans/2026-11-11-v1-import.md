## 2. Design

### 2.1 Who does what

- **The plugin knows v1.** It holds the SQL for the v1 tables and the mapping from v1 rows to
  FHIR resources. Nothing about v1 goes into CE's own code (AGENTS.md §8).
- **CE knows how to run an import.** It reads pages from the connector, hands the rows to the
  plugin, saves what comes back, and keeps the progress. This part is generic, so a DISA
  plugin can use it later.
- **The plugin never sees the database password and never opens a connection.** The plugin's
  page (an iframe) never supplies SQL. SQL comes only from the signed WASM, and CE checks every
  statement is a plain SELECT (`validateSelectSql`) before running it.

### 2.2 The contract between CE and an import plugin

A plugin that can import declares it in its manifest (`payload.importSource`, optional, so
existing signed bundles stay valid) and asks for a new capability, `host:import`. The admin
approves that at install, like any other capability.

Three WASM entrypoints, JSON in and JSON out:

| Entrypoint | CE sends | Plugin returns |
|---|---|---|
| `import_queries` | `{ options }` | `{ keyQuery: { sql }, detailQueries: [{ name, sql }] }` |
| `import_checks` | `{ options }` | `{ checks: [{ id, sql }] }`, each SQL returning one row |
| `import_map` | `{ keys, rows: { <name>: [...] }, options }` | `{ groups: [{ key, resources: [...], error? }] }` |

- `keyQuery.sql` returns one column of keys in ascending order. It uses two tokens that CE
  fills in: `{{after}}` (the last key of the page before, as a quoted literal) and `{{limit}}`.
  This is keyset paging, so page 600 costs the same as page 1. (`v1-push` uses `OFFSET`, which
  gets slower the deeper it goes.)
- Each detail SQL uses `{{keys}}`, which CE fills with the page's keys as quoted literals.
- CE turns SQL Server date values into wall-clock text with no zone (`2024-03-05T14:30:00.000`)
  before the plugin sees them. v1 stores local time, and the plugin adds the UTC offset the
  admin chose.
- One `group` per source key, so a failure is tied to one request.

### 2.3 The import run

- Lives in `@openldr/bootstrap` (`import-run.ts`). The route, the broker and the CLI all call it.
- One loop: read a page of keys, read the detail rows, call `import_map`, save the resources,
  write progress, repeat. It holds one connection for the whole run.
- Progress is a document in the existing `plugin_data` table (collection `import-runs`). **No new
  migration.** It records status, the last key done, counts, and when it started.
- Failures go in `plugin_data` too (collection `import-failures`), as key plus an error code.
  Never a row value or a patient field. Capped at 1,000 entries; the count keeps going.
- **Stop and resume.** Stop sets a flag the loop reads at the next page. Resume starts from the
  last key done. Saving uses the resource ids the mapping produces, which are fixed per request,
  so importing a request twice updates it and does not duplicate it.
- If the server restarts mid-run, the run shows as interrupted and can be resumed.
- **Dry run.** Reads and maps, saves nothing, reports what would fail.
- One run at a time per plugin and connector.
- Every start, stop, resume and finish is audited.

### 2.4 What the admin sees

A page added by the plugin, "v1 import", with these steps:

1. **Source.** Pick a Microsoft SQL connector. Runs the connection diagnosis (slice 2).
2. **Checks.** The four v1 tables exist; how many requests, results and AST rows; the date
   range; how many facility codes in v1 are not in CE's facility register yet.
3. **Options.** UTC offset for v1's local times (suggested from the lab's time zone), an optional
   date range, optional panel codes. No free-text SQL.
4. **Dry run.** A sample of requests, with the count that would fail and why.
5. **Import.** Progress, rate, failures list, Stop. A stopped or interrupted run shows Resume.

CLI, for headless labs:

```
openldr import start --plugin openldr-v1-import --connector <id> --option tz=+02:00 [--limit n] [--dry-run]
openldr import status [run-id]
openldr import stop <run-id>
openldr import resume <run-id>
```

### 2.5 The mapping port

The mapping moves from TypeScript to Rust, because every CE plugin is Rust and the build
already handles Rust. That makes two copies of the mapping. To keep them the same:

- The Rust tests use **golden files**: synthetic v1 rows in, the exact FHIR resources the
  TypeScript produces out. The files are generated once by running the TypeScript, and
  committed with the plugin. They hold no real patient data.
- A changed mapping in `cdr-toolchain` means regenerating the files. The Rust tests then fail
  until the port matches.

```ts

export function fillDetailQuery(sql: string, keys: string[]): string;   // quoted literals, '' doubled
export function toWallClock(value: unknown): unknown;                  // Date -> 'YYYY-MM-DDTHH:mm:ss.SSS'
export interface ImportRun { id: string; pluginId: string; connectorId: string; status: 'running'|'stopping'|'stopped'|'completed'|'failed'|'interrupted'; dryRun: boolean; options: Record<string,string>; pageSize: number; limit: number | null; cursor: string | null; counts: { keys: number; imported: number; failed: number; resources: number }; startedAt: string; updatedAt: string; finishedAt: string | null; lastError: string | null; startedBy: string }

  start(input: { pluginId: string; connectorId: string; options: Record<string,string>; pageSize?: number; limit?: number; dryRun?: boolean; actor: string }): Promise<ImportRun>;
```

- Connector type must be in the plugin's `connectorTypes`.

## 4b. Slice 4 as built (2026-11-11)

Two facts the plan asked for, read from the code before the run loop was written:

- One bad resource fails the whole save call (`packages/db/src/persist.ts:38`). So the run saves
  one source key at a time, and a bad record fails only its own request.
- A resource with a known id updates in place and adds a history version
  (`packages/db/src/fhir-store.ts:251`). So importing a request twice does not duplicate it.

Changes from the plan above, each with its reason:

- **An admin must allow each connector for a plugin.** The capability alone would let a plugin
  read any SQL Server connector while an admin has its page open. `openldr import allow` grants
  one connector; the studio screen for it comes with slice 5b.
- **Host-owned plugin data.** Runs, failures and the allow list live in `plugin_data` collections
  that start with `__`. The broker refuses plugin storage ops on those, so a plugin page cannot
  forge a run or grant itself a connector.
- **No server start hook.** A run with no progress for five minutes that this process is not
  driving reads as `interrupted` and can be resumed. This also works when the CLI drives a run
  while the server is up.
- **SQL Server only for now.** `importSource.connectorTypes` accepts `microsoft-sql` alone. Literal
  quoting and date handling are written and tested for it. Widen the list when a plugin needs
  another database, together with those two.
- **`import.diagnose`, not `connectors.diagnose`.** The result names the host and port, so the
  broker only runs it for a connector allowed for the calling plugin.
- **A per-request failure keeps a code, never text.** A plugin error that is not a bare code is
  stored as `MAPPING_FAILED`; a save error keeps only its error code.
- **Not built in slice 4:** the studio screen for allowing a connector, and user docs. Both land
  with slice 5b, when a plugin exists that can use them.

Proof, by layer:

- Unit and service tests with a fake plugin and fake source over pg-mem: `import-sql.test.ts`,
  `import-run.test.ts`, `plugin-broker.test.ts`, `packages/cli/src/import.test.ts`.
- **Real SQL Server 2025** (throwaway container, synthetic rows, 2026-11-11): 7 requests in pages
  of 3, 3 and 1; a key containing a quote; a request with two rows paged once; `datetime` and
  `datetime2` values arriving as wall-clock text; a lower-case key sorted by the server's
  collation and still found by keyset paging.
- HONEST NON-PROOF: no real wasm plugin, no real save into CE's FHIR store, no timing on real
  v1 data. Slice 5a provides the plugin; a run on the operator's v1 data proves the rest.

## 5. Risks, stated plainly

1. **The mapping has never been accepted by a live CE.** Only dry runs exist. A port copies
   whatever is wrong with it. See question 1.
2. **Speed is unknown.** Nobody has measured CE saving 320,000 requests in process. HONEST
   NON-PROOF until a timed run of a few thousand requests on the real v1 data.
3. **The Rust build is not set up on this machine.** `rustup target list --installed` shows no
   `wasm32-wasip1`. The first build downloads it from the official Rust servers. The existing
   build script also has Windows default paths.
4. **Two copies of the mapping.** Golden files catch drift only when someone regenerates them.

## 6. Not in this plan

- DISA. It needs the `disalab` blob decoder inside the plugin. It reuses slice 4 unchanged.
- Comparing imported data back against v1 (the `compare` gate in `cdr-toolchain`).
- Scheduled or repeating imports. This is a one-time migration with resume.
- Writing anything to the source database.
