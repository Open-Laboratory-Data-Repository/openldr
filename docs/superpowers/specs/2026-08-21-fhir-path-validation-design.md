# FHIR path validation for form fields

Date: 2026-08-21
Status: design, approved for planning

## Problem

`FormField.fhirPath` is a free-text string that nothing validates. The seeded Facility form
carries several values that are wrong, and no test, lint rule, or type would have caught any
of them.

The trigger was the Facility form's administrative hierarchy. Zone binds `address.district`
and Region binds `address.state`. The app's own declared containment order is
`zone < region < district < council`, zone widest
(`apps/studio/src/facilities/useFacilityAdminSuggestions.ts:42`, from `FACILITY_ADMIN_LEVELS`).
FHIR R4 nests `country > state > district > city`
(`@types/fhir@0.0.44/r4.d.ts:34016-34034`). So the form puts the widest tier on the
second-narrowest element, and the tier below it on the widest element. A consumer reading the
exported Location concludes Region contains Zone.

## Two defect classes

They need different mechanisms, and conflating them is how this goes wrong.

**Structural.** The path does not exist, or it lies about shape. Present today in the shipped
samples:

- `identifier.value` on a Location. `Location.identifier` is `Identifier[]`
  (`packages/fhir/src/resources/location.ts:12`). The repo's only path writer, `setPath`,
  produces `{identifier: {value: 'X'}}`, an object where FHIR wants an array.
- `telecom.value`. Same problem, `ContactPoint[]`.
- `physicalType` bound to a reference field. `Location.physicalType` is a `CodeableConcept`.

A machine catches all of these.

**Semantic.** Zone on `address.district`. The path exists. The leaf is a string. The field is a
string. It is structurally perfect and describes the wrong thing. No generic FHIR validator
catches this. Only a domain rule or a human reading the element's own definition does.

## Why nothing caught it

- The FHIR Path field is a plain `<Input>`, no validation
  (`apps/studio/src/forms-builder/field-editor/MappingEditor.tsx:47`).
- The schema is `z.string().nullable()` (`packages/forms/src/schema/form-schema.ts:56`).
- Lint checks path collisions only, never whether a path exists
  (`packages/forms/src/lint.ts:44`).
- There is no agreed grammar. The Facility and Practitioner samples use unprefixed paths. The
  Patient and Requisition samples use prefixed. The input's placeholder advertises a third
  reading, `Patient.name`.

## Current blast radius

Small, which is why now is the cheapest moment to fix it.

`setPath` has zero callers. Nothing generic consumes `fhirPath`. The live consumers are four
hardcoded string comparisons: `ServiceRequest.code`, `ServiceRequest.identifier`,
`ServiceRequest.priority` in the extractor, and `ServiceRequest.subject` in
`apps/server/src/forms-routes.ts:39`. Facility saves route through `apiProperty`, not
`fhirPath` (`packages/db/src/facility-answers.ts:129`). Nothing exports a facility as a
`Location` yet.

The operator has confirmed a real FHIR export is planned, so these values will become
load-bearing.

## Rejected source: the local zod schemas

The obvious move is to walk `packages/fhir`'s zod schemas. It does not work.

Those schemas are deliberately partial and end in `.passthrough()`. `ServiceRequest` stops at
`specimen` (`packages/fhir/src/resources/service-request.ts:21`). It has no `locationCode`,
`note`, or `performer`. The shipped Requisition sample binds all three
(`packages/forms/src/samples/forms.ts:360,403,415`). A linter built on them would call three
valid R4 paths unknown on day one.

They validate what CE writes. They are not a description of R4.

## Design

### 1. Generated path table

A script walks `@types/fhir/r4.d.ts` with the TypeScript compiler API and emits a checked-in
table. `@types/fhir` is already a dependency, it is complete, and its JSDoc carries the
official element definitions.

Each row carries:

- the dotted path, resource-prefixed
- the leaf datatype name
- whether any segment on the way is an array
- the JSDoc first line, which is the official short definition

Scope controls:

- Depth capped at 3. Deeper paths are rare and the table would explode.
- An explicit resource-type allowlist, seeded from what `registerResource` already covers.
  This selects which resources appear in the table, not which of their elements. Every element
  of an allowlisted resource is emitted, which is exactly the completeness the zod schemas
  lack. Extending the list is a one-line change.
- Traversal stops at `Reference` and `Extension` to avoid recursion.

Regenerated by a `pnpm` script, with a test that fails when the checked-in file is stale.
Same discipline as `make:changelog`.

`address.district`'s JSDoc reads "District name (aka county)". That string is the single most
useful output of this whole piece.

### 2. Grammar

Resource-prefixed is canonical. `Location.address.district`.

The Requisition sample forces this. It declares `fhirResourceType: 'ServiceRequest'` and
carries `Specimen.type` fields (`packages/forms/src/samples/forms.ts:428`). An unprefixed path
cannot say which resource a field lands on, and multi-resource extraction is exactly what the
extractor already does.

Bare paths stay readable. `normalize.ts` upgrades them using the form's `fhirResourceType` on
load, so an existing form keeps working with no data migration for the grammar alone.

### 3. Structural lint rules

Three new codes in `packages/forms/src/lint.ts`, alongside the existing ones.

`unknown-fhir-path`. The path is absent from the table for its resource type. Catches typos and
invented elements.

`fhir-path-cardinality`. The path crosses an array segment with neither a numeric index nor a
`fhirDiscriminator`. Catches `identifier.value`. Stays quiet when a discriminator is present,
because that is how the writer will select the element. This rule pairs with the existing
`ambiguous-fhir-path` rule rather than replacing it.

`fhir-path-type-mismatch`. The leaf datatype cannot hold the declared field type. A `text`
field on a `CodeableConcept`, for example.

### 4. Admin-order rule

`facility-admin-order`. Where a form's fields carry an `apiProperty` in `FACILITY_ADMIN_LEVELS`,
the Address elements they bind must sit in the same containment order as the levels.

Keys on `apiProperty`, never on the display label, so renaming Zone does not defeat it. Reads
`FACILITY_ADMIN_LEVELS` from `@openldr/db`, the same import `useFacilityAdminSuggestions`
already uses, so the order has one source.

This rule is narrow by construction. It knows about facilities and nothing else. That is
accepted: it is the only mechanism that catches the semantic class by machine.

### 5. Builder UI

The FHIR Path input becomes a searchable combobox over the table, scoped to the form's
`fhirResourceType`. The selected element's definition renders below it in muted text.

Free text stays allowed. A gap in the generated table must never block an operator; the lint
rule reports it instead.

shadcn components only. Label left, input right, per `AGENTS.md` §5. No standalone buttons.

### 6. Correcting the Facility mapping

Rules ship at `error` severity, and the data is corrected in the same slice so nothing is ever
unpublishable. Lint errors already gate publish
(`canPublish={!hasErrors}`, `apps/studio/src/forms-builder/FormBuilderPage.tsx:240`).

| Field | Today | Corrected |
|---|---|---|
| Facility code | `identifier.value` | `Location.identifier.value` (discriminator unchanged) |
| Name | `name` | `Location.name` |
| Country | `address.country` | `Location.address.country` |
| Zone | `address.district` | `null` |
| Region | `address.state` | `Location.address.state` |
| District | `address.city` | `Location.address.district` |
| Council | `null` | `Location.address.city` |
| Status | `status` | `Location.status` |
| Level | `physicalType` | `Location.physicalType` |

This uses all four Address slots in their real containment order and drops the one tier with no
standard analogue, Zone. Council on `city` is a stretch, but `city` is defined as "city, town,
suburb, village or other community", which a council is far closer to than a district is.

Zone only exports honestly through `Location.partOf`. See Out of scope.

Two changes are needed to land this:

- `packages/forms/src/samples/forms.ts`, for fresh installs.
- Migration 089, for installed forms. Follows the 071/072/073 pattern exactly: a frozen
  snapshot of the prior shape, an exact-match guard so an operator's own edits are never
  overwritten, and a marker key so `down()` is a precise inverse. 089 is unclaimed on every
  local and remote branch as of this date.

`FACILITY_FORM_MIGRATION_BOUND_FIELDS`, which `packages/forms/src/samples/forms.test.ts` pins
the sample against, moves to the new snapshot.

## Out of scope

**IHE mCSD.** The standard answer to having more administrative tiers than `Address` has slots
is to stop using `Address` for the hierarchy. Each tier becomes its own `Location` chained by
`Location.partOf`, with the tier carried on `Location.type`. `Address` then holds only the
facility's postal address, and the Zone problem disappears.

That is the right destination. It is also a facility data-model change, not a validation
feature, and nothing consumes a Location export today. It belongs in the spec for the export
slice, not this one.

**Completing the zod schemas.** Not needed. The generated table is the path authority; the zod
schemas keep their existing job of validating what CE writes.

**A generic path writer.** `setPath` stays uncalled. Teaching it to honour discriminators and
array indices belongs with the export work.

## Verification

What each layer proves, and what it does not.

- Unit tests over the generator: given a fixture `.d.ts`, the emitted table has the expected
  paths, array flags, leaf types, and descriptions.
- A staleness test: regenerating produces no diff.
- Unit tests per lint rule, including the negative cases. A discriminated `identifier.value`
  must not fire `fhir-path-cardinality`. A renamed Zone must still fire `facility-admin-order`.
- A test asserting every path in every shipped sample form passes all four new rules. This is
  the regression that would have caught the original bug.
- Migration 089 gets the same test shape as 071 and 073: each prior era repointed, an edited
  form left alone, `down()` restoring exactly.

Not proven by any of the above: that a real FHIR consumer accepts the output. Nothing exports a
Location yet, so there is nothing to point at a validator. That gap closes with the export
slice.

Migration 089 must be verified on a real boot. pg-mem cannot catch a numbering gap.
