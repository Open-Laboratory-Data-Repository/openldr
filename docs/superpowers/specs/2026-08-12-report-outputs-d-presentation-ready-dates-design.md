# Root D — presentation-ready dates

Source: `docs/audit/2026-08-07-report-visual-design-audit.md`.
Closes the **date half of P0-08**. Closes the ambiguity half of **P1-04**.

## The problem

`packages/report-designer/src/render/draw.ts:196`:

```ts
m.set('date', now.toLocaleDateString());
```

No locale argument. So the date printed on a Ministry document is whatever the **server's** ICU
default produces. The audit saw `07/08/2026` and could not tell 7 August from 8 July.

This is not a cosmetic finding. The output depends on the machine the server happens to run on —
change the host's locale and the same report says a different date.

The reporting period beside it renders as raw ISO (`2020-01-01 – 2030-01-01`) because the daterange's
flat `from`/`to` tokens (`draw.ts:181-186`) are passed through untouched.

## What was checked first

RULE 0 pass before designing.

| Assumption | Finding |
|---|---|
| A shared date formatter already exists to reuse | **False.** `grep` over `packages/` finds exactly one `toLocaleDateString` — the defect itself at `draw.ts:196`. Nothing else in any shared package formats a date. |
| A timezone or locale setting exists | **False.** Nothing in `packages/config/src/`, and `LAB_IDENTITY_FIELDS` (`lab-identity.ts:52-57`) is exactly `name`, `address`, `contact`, `logo`. Printing a time with a zone would require inventing a setting. |
| The renderer receives a language signal | **False.** `RenderOptions` (`render/index.ts:30-45`) carries `now`, `identity`, `values` and nothing else, and the package is deliberately pure with no database reach. |
| Existing tests pin the rendered date format | **False, and worse — they are tautological.** `draw.test.ts:23`, `:32` and `:474` assert `expect(m.get('date')).toBe(NOW.toLocaleDateString())` — the expectation calls the same function as the code. They pass whatever the format is, including a wrong one. |

## Decisions taken

- **Month name, no new setting.** `12 Aug 2026`. A month *name* removes the day/month-vs-month/day
  ambiguity P0-08 actually reports, and needs no configuration. Time and timezone are **out of
  scope** — a time without a zone is worse than no time, and the zone would need a setting.
- **English only, and that is consistent, not a gap.** No language reaches the renderer, and the
  seeded designs' own text — titles, footer, and the metric and legend strings added by Root B — is
  already English in `SEED_DESIGNS`. A `locale` option no caller could supply would be a false
  affordance.
- **A hand-rolled month table, not `Intl`.** See below; this is the load-bearing choice.

## Design

### 1. One pure helper

New file `packages/report-designer/src/render/format-date.ts`:

```ts
/** `2026-08-12` -> `12 Aug 2026`. Anything that is not a plain ISO date is returned UNCHANGED. */
export function formatDisplayDate(value: string): string;
/** A `Date` -> the same display format, read in the host's local time. */
export function formatDisplayDateOf(d: Date): string;
```

Month names come from a literal twelve-entry array, **not** `Intl.DateTimeFormat`.

That is deliberate, and it is the whole point of the slice. The defect is that the environment
decides what the document says. `Intl.DateTimeFormat('en-GB', …)` narrows that but does not remove
it: on a small-icu Node build `en-GB` can fall back to another English locale and reorder the parts.
A literal month table removes that class entirely, and it is eight lines.

**Be precise about what becomes environment-independent, and what does not.** The *format* — the
order of the parts and the spelling of the month — stops depending on anything. The *calendar day*
still follows the host timezone, because `formatDisplayDateOf` reads local date components: a server
at UTC+3 at 01:00 prints today, one at UTC prints yesterday for the same instant.

That is correct behaviour, not a residual bug. The report is generated by the lab's own server, and
"generated on" means the lab's day. Reading UTC components instead would make a report generated at
01:00 local claim yesterday's date, which is worse. The point stands where it matters: two servers in
the same timezone can no longer disagree about what the document says.

### 2. Applied at exactly two token sites

Both in `paramMap` (`draw.ts:172-197`):

- `m.set('date', …)` becomes `formatDisplayDateOf(now)`.
- the daterange branch (`draw.ts:181-186`) passes its `from` and `to` through `formatDisplayDate`.

Nothing else changes. `interpolate` is untouched.

### 3. Only reformat what is actually a date

`from`/`to` are declared `text` and may hold anything. `formatDisplayDate` returns its input
unchanged unless it matches `^\d{4}-\d{2}-\d{2}$` **and** parses to a real calendar date.

Two cases this protects:

- **`UNSET`** — a declared-but-unset parameter renders the em dash `—` (`draw.ts:168-170`). It must
  stay an em dash, not become `Invalid Date`.
- **`2026-02-30`** — matches the shape, is not a date. Round-tripping through `Date` would silently
  print `2 Mar 2026`. Return it unchanged instead; a wrong date is worse than an ugly one.

### 4. What this does NOT touch

- **Date values inside table cells.** They arrive from SQL as strings and the renderer cannot tell a
  date column from a text one. Reformatting cell text would corrupt non-date columns.
- **The studio's date formatting.** 18 files format dates ad-hoc, some bare `toLocaleString()`, some
  hardcoded `'en-GB'`. Adjacent, not this slice (AGENTS.md §4).
- **Time, timezone, and release traceability.** P1-04's other half. It belongs with Root C, the
  document-status and control-block root, which needs the same setting.
- `packages/reporting`'s seeded designs. `scopePairs` already emits `'{{param.from}} – {{param.to}}'`
  with an en dash (`simple-design.ts:52`), which is what the audit asks for. No design changes.

## Consequence worth naming

`from`/`to` are reachable from **any** text element, because `elementValue` interpolates an unbound
element's `text` — including a `barcode` or `qrcode` payload (`draw.ts:502-513`). No seeded design
encodes a date in a symbol, but a lab-authored design doing so would get `12 Aug 2026` in the symbol
instead of `2026-08-12`. Accepted: the alternative is a second token namespace for machine values,
which nothing needs today.

## Testing

| What | Layer it proves | Layer it does NOT prove |
|---|---|---|
| `formatDisplayDate` over a table of inputs — valid ISO, the em dash, `2026-02-30`, `''`, a non-date string | the helper's contract | nothing about the renderer |
| **`formatDisplayDate('2026-08-12')` is byte-identical under a different `LANG`/`LC_ALL`** | the format no longer depends on the environment | ⚠ do NOT vary `TZ` in this test — the calendar day legitimately follows the host zone (see §1), so a TZ sweep would fail by design, not find a bug |
| `paramMap` with a fixed `now` asserts the **literal string** `12 Aug 2026` | the defect is fixed at the token layer | not the PDF |
| `paramMap` daterange asserts `from`/`to` are reformatted, and that an unset range stays `—` | the range half | — |
| Replace the three tautological assertions at `draw.test.ts:23,32,474` with literal expectations | that the tests now pin something | — |
| A rendered PDF, inspected | that the page reads correctly | — |

**The rendered-PDF check is required, not optional.** Root B shipped a metric string that every test
passed and that the page silently ellipsized. Render both AMR reports and read the scope panel.

Note `renderReportDesignPdf` takes an injectable `opts.now` (`render/index.ts:52`), so a
deterministic PDF needs no clock mocking.

**HONEST NON-PROOF in advance:** no test here proves behaviour on a small-icu Node build. The month
table means there is nothing locale-dependent left to break, which is why the table was chosen over
`Intl` — but that is an argument, not a test.
